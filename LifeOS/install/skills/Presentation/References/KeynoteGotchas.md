# Keynote gotchas

Verified failures from Keynote builds, each with its date. The build guards against most of them in code; these say why, so a run does not undo the guard. Which of the install's own decks each one came from is install history, kept in `<configRoot>/LIFEOS/USER/CUSTOMIZATIONS/SKILLS/Presentation/History.md` when present.

## Gotchas

- **A picture's frame is not what the audience sees; its drawing is.** A slide (2026-10-02) bled a 16:9 image whose drawing filled only part of its frame, and every box-based check passed because the image's frame covered the whole slide. Two rules now hold in code: art bleeds edge to edge only when its drawing covers the frame (`Layout.ts isScene`), and every build judges the rendered slide pixels, failing any slide where one block of bare ground is over 26.5% of the slide (`pixelIssues`). Never loosen that threshold to pass a deck; change the slide.
- **Generated art's empty paper reads as slide whitespace.** Art is drawn on paper the colour of the slide, so a drawing that fills half its canvas looked like a thumbnail floating in space on split slides (2026-10-02: bullets at the top, a small picture, much of the slide empty, diagrams unreadable). `Keynote.ts` now trims each picture to its drawing (`Layout.ts prepareImage`, cached in `.layout-cache/`) and sizes what is left. 16:9 art that bleeds edge to edge is not trimmed.
- **A layout problem fails the build after the deck is written.** `Keynote.ts` exits 4 and lists each slide with what is wrong; `LAYOUT.json` in the talk folder holds every slide's measured rectangles. Fix the slide (a full slide for a wide picture, a taller picture, fewer bullets) rather than loosening the thresholds in `Layout.ts`. A soft-picture warning (a small source shown large) does not fail the build; find a larger source when one exists.
- **Keynote cannot round an image through scripting, so the build bakes the corners in** (2026-10-03, a film-clip slide showed sharp-cornered footage and its film credit as the subtitle). `Keynote.ts` passes every `media` picture through `Layout.ts roundCorners` at 12 pt for the size it will be shown: a still becomes a PNG with transparent corners, a GIF gets ground-coloured corners because GIF transparency is on or off and would leave jagged edges. Sourced files stay square on disk. A media subtitle that reads as a credit (a year in parentheses, "directed by", "screenshot") fails design validation; the credit goes in `source`.
- **Every animation must start by itself; Keynote's default waits for a click.** Keynote gives each inserted GIF a "start movie" build that waits for a click, and its scripting dictionary cannot change it (the speaker's words, 2026-10-01: "I won't remember to do that"). `Keynote.ts` runs `KeynoteAutoplay.ts` on every build to patch the build chunk; the archive fields it sets are in that tool's header. A deck edited and saved in Keynote keeps the setting; a deck built by any other path needs `KeynoteAutoplay.ts <deck>` run on it.
- **Starting by itself is not starting at once** (2026-10-17, the speaker: "some of these are taking longer to start than we have for the slide"). AnimatedDiagram GIFs open on the finished drawing, hold it about 3.7 s, fade, then draw; screen captures held their first frame about 1.3 s. Every build passes each GIF through `Layout.ts startOnMotion`, which rotates the loop to open on its motion (past a hold and the fade after it) and fails the build if anything still sits more than `MAX_GIF_LEAD` (0.5 s) before moving. Results are cached per file in `.layout-cache/`, because reading a long clip's frames takes minutes.
- **Autoplay is proven by `KeynotePlayback.ts`, never by `KeynoteAutoplay.ts --check`** (2026-10-04). `--check` rereads the field it wrote, and it passed while the deck the speaker presented, an unpatched copy Keynote had autosaved into iCloud, waited for a click on every GIF. `KeynotePlayback.ts` has Keynote export the deck as HTML and fails any click step before the slide advance; every build runs it, and `bun Tools/KeynotePlayback.ts <deck.key>` checks a deck the speaker saved. Why the export and not the slideshow is in its header.
- **Keynote autosaves an untitled document into its iCloud Documents folder during a long build** (2026-10-04: unpatched copies, each written seconds before its build finished). The build saves its document to the local output path before the first edit, and a build that sees a new deck appear in the iCloud folder fails and names it.
- **A picture on two slides reads as a duplicate slide.** The build fails a picture on two slides, back to back included, and a slide whose rendered picture looks like another's under a different file (a still of a page beside a GIF of the same page; `Layout.ts lookalikeIssues`, measured 2026-10-04, when the speaker found such pairs after the name check passed). A callback the speaker asked for ("show that slide again") is marked with `--set N reprise yes`.
- **Talk files arrive in the speaker's own shorthand** (format: `TalkFiles.md`). Single `-` separators once merged several talking points into one section and stage notes were about to be read aloud (2026-10-02). Until 2026-10-03 headings were only a title hint, so a file structured by headings with no dashes came out as one talking point; every heading now starts one. The heading-split stays hash-compatible: a heading at the top of a dash section keeps its old design key.
- **A long Keynote session can wedge Keynote.** After a long run of builds it sat idle with a large resident footprint, no windows, and every AppleEvent timing out (2026-10-02). The build now asks Keynote first and stops with a plain message; quit Keynote and rebuild. A wide picture on a split slide is fixed with `--set <slide> kind full`, which drops its bullets.
- **Keynote turns an inserted animated GIF into a movie object.** It lands in `slide.movies`, not `slide.images`, keeps the GIF file, and loops by default. Reading `slide.images` after the insert fails with "Invalid index" (2026-10-01). `Keynote.ts` handles it. A JXA or AppleScript `movie` insert of an MP4 fails outright ("Can't convert types"), so GIF is the scriptable way to put motion on a slide.
- **Slide numbers are not talking point numbers.** One talking point can span several slides. `--move` takes talking point numbers and `--set`/`--redo-art` take slide numbers; `Keynote.ts --list` prints both. Art slugs come from the section hash, so moving talking points never orphans art.
- **Some slides are diagrams.** A slide that explains how something works gets art type `diagram` and goes through Art's TechnicalDiagrams intent, with labels and insight callouts and no title block (`untitled: "deck"` in its spec). The rest are essay illustrations with no text at all. Mixing the two up gives a diagram with no labels or an illustration full of garbled words.
