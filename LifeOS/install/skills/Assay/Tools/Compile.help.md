# Compile.ts — write an ISA's evals

Writes one eval per criterion that has none (a manual or invalid row is not an eval, so those criteria compile; the definition is `idsWithEval` in `LIFEOS/TOOLS/lib/IsaScope.ts`, shared with `EvalCensus --without-eval`), or whose text changed since its eval was compiled, sized to the cheapest tier the criterion allows (code, glance, rubric or pairwise judge; a compound criterion is flagged to split). The model call runs at level `max` through Inference.ts, in one call or parallel batches. Shared check libraries the ISA inherits (`output:` in frontmatter, or inferred from `artifact:`) compile in code with no model call. Compile never writes the ISA.

## Usage

```
bun skills/Assay/Tools/Compile.ts <ISA.md> [--dry-run] [--json] [--write] [--only ISC-n[,ISC-m]] [--caller <name>] [--batch N]
bun skills/Assay/Tools/Compile.ts merge <ISA.md> [--dry-run] [--json]
bun skills/Assay/Tools/Compile.ts split <ISA.md> [--dry-run] [--json]
bun skills/Assay/Tools/Compile.ts --help
```

`merge` folds `Evals.proposed.md` into the ISA (main session only; `CompileMerge.ts`): Test Strategy rows for the compiled criteria, replacing a criterion's old rows only when the proposal covers it (all of them when compile already owns it, else only invalid, manual and `eval:#` rows), and `## Evals` blocks and ledger lines with their criterion_sha (the section is created just before `## Articulation Log`, or at the end). `Glance registrations` and splits stay reported, never applied. It refuses, writing nothing, when the ISA changed since the proposal was compiled, when a criterion would end with two evals, or when the merged ISA does not parse the merged rows and blocks. After a successful write it rewrites `Evals.proposed.md` to hold only what it did not apply (splits, refusals, `Glance registrations`, inline rubrics, library notes) under a header carrying the ISA's new revision and the word `merged:`, and removes the file only when nothing unapplied remains. A proposal with no rows or blocks (only splits or refusals) is marked the same way without touching the ISA, and rows and blocks the ISA already holds byte for byte leave it as it is. `--dry-run` checks everything and writes nothing. Exit 0 merged · 1 refused · 2 usage.

`split` applies the proposal's `## Split these` (main session only; `CompileSplit.ts`). Each `- <id>: <reason>` with its indented `- <part>` lines becomes the ID-stability shape: the parent line gains a `[container] ` prefix (once) and the parts are inserted directly beneath it as `<id>.1`, `<id>.2`, …, two spaces deeper (at the content column, at least three spaces, under a numbered parent), each with the parent's checkbox. An indented line with no list marker continues the reason or part above it. Nothing renumbers and Test Strategy, Evals and Decisions are untouched; an ISA with an `## Articulation Log` gets one `- <date>: refined: <id> split into <id>.1 / <id>.2 (compile split)` line per split. It writes atomically only after the rewritten ISA parses to the old criteria plus exactly the new children, then drops the applied entries from the proposal (keeping the rest, as merge does). It refuses the whole file, writing nothing and listing every reason, when the ISA changed since compile, the proposal still carries unmerged rows or blocks, a parent is not found or is a table row, a parent already has nested children, or a child id already exists. `--json` prints `{ok, isa, applied:[{id, children}], refusals, written, dryRun}`. Exit 0 split (or nothing to split) · 1 refused · 2 usage.

A `[container]` criterion with nested children needs no eval of its own: compile skips it (never sent to the model, never reported missing) and `EvalCensus --without-eval` does not count it, so after a split the next compile compiles only the children. A `[container]` with no children is an ordinary criterion.

Across the estate, `CompileEstate.ts` runs compile on every in-scope ISA (`Tools/CompileEstate.help.md`).

## Flags

- `--dry-run` lists what would compile and the inherited library checks; no model call.
- `--json` prints the full result (criteria states, compiled evals, splits, refusals, registrations, call count, latency, `written`).
- `--write` puts the proposal in `Evals.proposed.md` beside the ISA for the main session to merge. Never ISA.md. When the file there is a remnant (`merged:` header), its unapplied items are carried into the new proposal: `Glance registrations` and inline rubrics not already in it, and split or refusal entries for criteria this run did not take up that still lack an eval.
- `--only ISC-n[,ISC-m]` (repeatable) recompiles just those criteria, whatever their state. An id not in the ISA is a usage error.
- `--caller <name>` is the judgment caller compiled questions name (default `bunker-glance`). Questions start in shadow; the `registerQuestion` calls are reported, never made.
- `--batch N` sets criteria per model call (default 8).

## Output

The proposal, on stdout or in `Evals.proposed.md`: Test Strategy rows, `## Evals` blocks each carrying `# criterion_sha:`, ledger lines for one-line rows, then sections for inherited checks waiting on a binding, checks switched off, library problems, `Glance registrations`, criteria to split, and criteria refused twice. A summary line goes to stderr.

Every emitted eval is checked in code before it is shown:

- Paths are relative to where they run: code checks, rows and pairwise commands from the ISA's folder (the config root under `probe_cwd: config-root`), glance producers from the ISA's folder. An absolute path inside that folder is rewritten to `./<rel>`; a home path outside it is refused.
- An `eval` stage names a suite SuiteManager lists, or, when none fits, carries an inline anchored rubric (`id`, `dimension`, `rubric`, `anchors`, `subject`, optional `scale` and `threshold`). Each rubric grades one dimension, anchors every level 1..scale, and reads its subject from the ISA's folder. A quality with several dimensions gets one rubric per dimension; a dimension joining two qualities ("calm and premium"), or two rubrics on the same dimension, is refused. Anchors given as an ordered list become the level map. Inline rubrics are listed in the proposal as provisional until each one's calibration earns.
- A `pairwise` stage's first candidate, the champion, is a file that exists or the slot `champion:last-accepted`, which Bunker fills with the last accepted output at run time (and skips, never passes, when there is none).
- A judged eval whose output is a file, page or screenshot (a URL, or a path ending in a page, image, video, audio, `.md` or `.txt` extension, found in a rubric subject, a glance producer, a pairwise candidate after the champion or a judged row's tool cell, and, when a suite judges, in the block's code stages or the criterion's code rows, since a suite names no subject; never the ISA itself) is a block: its rubric stage, then a `pairwise` stage whose first candidate is `champion:last-accepted`. A missing pairwise stage, one placed before the rubric, or one naming a fixed champion file after the rubric is refused. A pairwise stage or row against `champion:last-accepted` with no rubric is refused too: with no champion recorded it skips, and only a rubric can decide (ISC-54). A pairwise check with a fixed champion and no rubric still stands as a block stage (ISC-43); as a row it is refused, since a row has no earlier stage to write its candidate (ISC-57). A judged eval with no such output keeps its rubric alone. The rule is `LIFEOS/TOOLS/lib/PairwiseGap.ts`, the same one `EvalCensus --pairwise-gaps` counts with; a compiled eval that has a gap reads as state `gap` and is recompiled. When a suite judges and the block names no output, the criterion's code rows and then its own text are read, so a suite stage standing alone never hides the page its criterion is about.
- Every pairwise candidate after the champion is this run's output (ISC-57): an earlier code stage of the same block writes it, as the operand of `--out`, `--output`, `--outfile`, `-o` or a `>` redirect, and the candidate names exactly that path (`./x` and `x` are the same). A copy is not a write: a `>>` append, or a redirect of a pipeline starting with `cat`, `echo`, `printf`, `head`, `sed` and the like. A page is captured with one plain call of the sanctioned browser tool on a page the eval grades (a rubric subject, glance producer, code gate, the criterion's text or code rows), `bash skills/Interceptor/Tools/Capture.sh <url> --out ./.assay/captures/<isc>.png`, optionally with `--full`, `--pixel` or `--scale N`: nothing chained to it, never `--current` or `--allow-unchecked`. curl or wget writing a page, Playwright, Puppeteer, screencapture, and any other command writing the image of a page the eval grades are refused, while a build that reads a URL as data and writes its own non-image file is a build. A candidate no earlier stage writes (a file already on disk, one `test -s` only names) is refused. This is a read of the command text: a build script that copies a file inside itself is not caught, except for page images, which only Capture.sh may write. Project repos running captures should ignore `.assay/`.
- A recompile (a criterion that already has an eval: state changed, broken, gap or forced) is held to that eval (ISC-58): it names every capturable output the previous eval named in any stage or row (the champion and what it compared aside); it keeps at least as many code gates on each of those outputs (a curl status or content check; a capture is not a gate), compared by count so a gate may be rewritten but not dropped; and when the previous eval was judged by a rubric or suite, whether or not it named an output, it keeps a rubric or suite stage, never a glance question or code check alone. The prompt says what to keep up front; a refusal says what was dropped. To let a criterion really drop its output, remove its old eval first, so the next compile is a first compile.
- Every LifeOS script a command names is one Bunker finds (ISC-59). Bunker runs a `skills/...` or `LIFEOS/...` script from the config root when the probe directory does not have it, wherever the command starts it: at the start or after `&&`, `||`, `;`, `|` or `(`, behind `VAR=value` prefixes, interpreter flags and `bun run` (`LIFEOS/TOOLS/lib/ProbeCommand.ts`). So compiled evals name LifeOS tools by their path under the config root, never by an absolute or home path. A started script that resolves from neither place is refused, and so is a LifeOS tool the probe directory lacks in any other position (after a `cd`, inside quotes, as an argument), since Bunker never rewrites it. Glance producers and rubric subjects run from the ISA's folder and may name only scripts inside it or under `LIFEOS/TOOLS` (the producer rules), so the parser refuses a `skills/...` script there.
- The tier guard, the code-check refusals and the M1 parser (`parseEvalsText`) must all pass.

A criterion that fails is regenerated once with the reasons, then reported. A broken block is never emitted.

## Exit codes

- `0` compiled, or nothing to compile.
- `1` a criterion was refused twice, or a library check has a problem.
- `2` usage error, or inference unavailable.
